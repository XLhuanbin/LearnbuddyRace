### 2.1 本地对象库损坏（先于本次操作就存在）

第一次合并 B 时报 `Could not read <sha>` / `unable to read tree`。诊断结果：

- `git fsck` 报 **102 个对象缺失**（64 blob / 30 tree / 8 commit），且从 HEAD 可达；

**修复方式（只增不删）**：重新克隆一份完整对象库到 `.build/fresh.git`（用

已确认它**不被任何工作分支引用**（`git log --all --find-object` 查无）、只挂在旧 reflog 上，可忽略。
随后 `git restore .` 把 29 个 docs 文件恢复，工作区干净。

## 3. 旧缓存迁移：补两条证据门槛（第 2 项）

原先的迁移只认「旧标签」，导致：
① 旧字段写了 `status: ok/verified` 就**直接当「可核验」**——即使引文缺失或未定位；
② 旧关系写了 `assertedBy: explicit`，或仅仅「引文能定位」，就**直接当「原文明示」**。
两者都会让界面显示比证据更强的结论（字段还会被 `Library.verifiedOf` 算进「已核验字段数」）。

### 改动（`src/core/cache.ts`）

| 函数 | 新规则 |
| --- | --- |
| `migrateMethod` | `ok/verified` 只有在 **`evidence.verified === true` 且有值**时才保留 `verified`；有值但证据不成立 → `unverified`（note 写明原因）；无值 → `missing` |
| `migrateRelation(r, methods?)` | 「原文明示」必须**引文已定位 且通过 `assessRelationEvidence` 充分性判定**（例如引文得指名被继承方法、有继承/组合措辞）；拿不到方法信息或不足以判定 → `candidate`，并在 `stateAdjusted` 里写明降级原因；旧 `assertedBy: explicit` 不再被直接采信 |
| `normalizeCorpusIndex` | 迁移关系时**传入 methods**（充分性判定需要方法名） |
| **新增** `normalizeRestoredData(methods, relations, papers)` | 本机恢复路径的统一归一：迁移 + **按当前规则重跑关系证据校验**（`revalidateCachedRelations`） |

### 刷新恢复也要过证据校验（`src/App.tsx`）

原先三条加载路径里**只有预置语料加载**跑了证据校验；两条**本机恢复**路径（初始化恢复、删除失败后的回读）
只做迁移、不校验。现两处都改为调用 `normalizeRestoredData`。
说明：关系充分性判定只依赖引文与方法名、**不需要论文全文**，因此恢复时无须先读全文，不存在「读不到全文就误降级」的风险。

### 修正迁移测试的错误期望（`scripts/verify-corpus-migration.mjs`）

该脚本原有 3 处断言**把错误行为写成了期望**，已改正并补两个正例（防止门槛变成一律降级）：

| 原断言 | 现断言 |
| --- | --- |
| `researchTask: ok → verified` | `ok` 但**无引文** → `unverified`（并断言 note 写明原因） |
| `assertedBy=explicit → explicit` | 引文不足以支撑（未指名被继承方法）→ `candidate`（并断言 `stateAdjusted` 有可读原因） |
| 无标签 + 引文未定位 → `inferred` | → `candidate`（不冒充任何正向结论） |
| —（新增） | `ok` + 引文已定位 → 仍 `verified`；引文充分 → 仍 `explicit` |

结果：**25/25 通过**，且**两个预置缓存的迁移幂等性仍然成立**（方法与关系前后语义一致）
⇒ 新的证据门槛**没有改动任何真实预置数据**。
