## 一、第二阶段新增能力（均已实现并通过程序校验 + 端到端走查）

### 亮点一：证据绑定

- 字段状态改为四态，且与界面文案一一对应：**可核验**（引文已定位）/ **待人工核对**（引文未定位）/ **未找到证据**（模型未给引文）/ **缺失**（论文未报告或未提取到）。
- 证据弹层展示：论文名称、页码（程序定位得到，不采信模型自报）、章节（启发式）、原文上下文（前后约 420 字符，高亮引文）。
- 未通过校验时**不显示页码**，改为展示「实际匹配到的原文位置」，说明模型引文的哪一部分是真的。
- 页码程序校验：模型自称页码与定位结果不一致时标为「页码与定位结果不一致」；超出论文页数时标为「页码超出论文数」，界面一律以程序定位结果为准。

### 亮点二：不可比检测

- 新增结构化实验条件：数据集、数据划分、评价指标、额外训练数据、预训练模型、实验设置、算力/训练时长（7 个维度，各自带引文与页码）。
- 可比性判断**由规则计算**（`src/core/comparability.ts`），不交给模型自评，因此每个结论都能说明依据：
  - 数据集 / 指标：完全一致 → 可直接比较；部分重叠 → 只能有限比较；无共同项 → 不能直接比较；
  - 额外训练数据：不一致即**不能直接比较**；
  - 实验设置：先识别评估协议（微调 / 零样本 / 少样本 / 蒸馏 / 从头训练），协议不重叠 → 不能直接比较；协议一致但超参不同 → 可直接比较并说明差异；协议无法识别 → 信息不足；
  - 数据划分 / 预训练模型：不一致 → 只能有限比较；
  - 算力/训练时长：只用于说明「能否确认可运行性」，不参与性能可比性判断。
- 每个维度都列出：结论、具体差异、判断依据（区分「原文证据 / 信息缺失 / 判定规则」）、缺失信息。
- 条件不一致时明确禁止直接比较数值；即使条件一致，系统也不自动排名。

### 亮点三：方法关系可信度

- 关系可信度改为三档，**不使用未校准的置信度百分比**：**原文明示** / **系统推断** / **待核查**。
- 程序强制规则（`src/core/validate.ts`）：
  - 原文明示必须有定位成功的引文，否则降级为「待核查」；
  - 引文即使可定位，若既不含被继承方法名、也无引用标记、也无继承/改进措辞（如 based on / builds upon / improvement over），判为「关键词相似而非技术继承」并降级；
  - 系统推断必须有实质推断理由（过短或仅凭共同关键词归类则降级）；
  - 关系两端方法名缺失则降级为「待核查」。
- 关系详情展示：来源论文、支持片段（可打开完整上下文）、AI 判断理由、可信度含义、以及**程序调整可信度的记录与原因**。
- 人工修正：可改关系类型、可信度与理由，可删除、可人工新增关系；保留 **AI 原判定**并可一键恢复；人工改动会被标记。

### 亮点四：根据用户条件进行方法决策

- 输入：基础、研究目标/兴趣、可用时间、计算资源、具体目标。
- 输出：**候选方法**（匹配度 条件匹配 / 有条件可用 / 无法判断）、**阅读顺序**、每条推荐的理由（标注依据来源：你的条件 / 论文 / 信息缺口）、适用条件、缺失信息、以及「条件敏感性」说明。
- 论文未报告算力时置 `computeReported=false`，明确说明无法确认可运行性，不推测。
- 下载的算力信息（如 8×P100 3.5 天、1024×V100、8×16GB V100 90h）均带原文证据页码。

### 亮点五：跨论文分歧与待调查问题

- 发现类型四档：**结论分歧（条件一致）** / **可由条件差异解释** / **共同提到的局限** / **当前材料未发现**。
- 程序强制复核：模型若把条件不一致的论文对判为「结论分歧」，系统会**强制降级**为「可由条件差异解释」并列出具体条件差异。
- 每条发现展示：涉及论文、双方结论与原文片段、条件差异、可能解释、下一步核查动作、以及固定声明。
- 同时输出「已检查的论文对」清单（含每对的可比性结论），用于证明没有为了展示而制造冲突。
- 共同局限的声明明确写为「当前材料中存在待调查问题，不代表整个领域存在研究空白」。

### 程序校验层（新增，独立于模型）

`src/core/validate.ts` 产出问题清单（字段缺失 / 未提供引文 / 引文无法定位 / 引文过短 / 页码不一致 / 页码无效 / 条件无法确认 / 关系被降级 / 关系缺少依据），
在论文库中逐条展示，并在状态页汇总统计。所有问题都说明「系统已做了什么处理」或「需要人工做什么」。

## 三十三、2026-09-26 重新加载案例不再丢失人工修正（第十轮，数据安全）

用户按真实操作顺序实测：**「重新加载演示案例」会把方法人工修正与关系人工修正一起丢掉**（刷新后更明显）。
先复现再改，复现与修复证据见 `docs/VERIFICATION.md` §V44；新增回归 `npm run verify:reload`
（`scripts/verify-cache-reload-safety.mjs`，20 项，独立 Chrome 数据目录 + 直读 IndexedDB）。

### 复现证据（改代码之前）

| 步骤 | IndexedDB 实测 |
| --- | --- |
| 加载视觉案例 | 论文 5 / 方法 5 / 关系 10 |
| 界面修正 ResNet「研究任务」 | 方法 `overrides=1`（`researchTask → 人工修正-回归测试值`） |
| 关系图修正一条已有关系（改为 `extends`） | 关系 `userEdited=true, type=extends, rationale=人工修正关系的理由-回归测试`，**id 与缓存关系相同**（用户要求的「同 ID」情形正是默认情形） |
| 点「重新加载演示案例」 | `overrides=0`（丢失）；关系变回 `type=unclear, userEdited=false`（被缓存版本覆盖） |
| 刷新页面 | 同上，仍然丢失；界面「已人工修正」标记消失 |

### 根因（两处，都是「内存里保住了、库里丢了」）

1. **方法**：`loadSample()` 用 `repo.saveMethod(cachedMethods[i])` 同 ID 覆盖写。缓存里的方法**永远没有 `overrides`**，
   于是用户逐字段核对过的修正被直接覆盖掉。
2. **关系**：`replaceRelationsInScope()` 在内存里已经做到「人工优先」（`manualIds.has(id)` 就跳过），
   但落库那一行写的是 `repo.saveRelations(cachedRelations)` —— **原始缓存数组**，把同 ID 的人工关系覆盖掉了。
   内存与库不一致，所以「重载后立即看」和「刷新后看」都会丢。
   另外 `saveRelations` 与 `deleteRelations` 是**两次独立事务**，「原子替换」只是说法。

### 修复

- `src/core/corpus.ts`
  - `replaceRelationsInScope()` 增加 `write`（= incoming 去掉「与人工关系撞 ID」的那些）与 `deleteIds`
    （已排除 write 的 ID，避免同一事务里先写后删）。**落库必须用 `write`，不是 `incoming`**。
  - 新增 `mergeCachedMethod()` / `mergeCachedMethods()`：同 ID 覆盖写方法时保留 `overrides`（用户产生的东西），
    AI 字段值仍按缓存更新。
- `src/core/storage.ts`
  - 新增 `txApply()`：**跨 store 的单个 IndexedDB 事务**（`db.transaction([stores], 'readwrite')`），任一操作失败整个事务 abort。
  - 新增 `repo.applyAtomic(ops)` 与 `repo.swapRelations(puts, deleteIds)`（关系的写入+删除同事务）。
- `src/App.tsx`
  - `loadSample()`：合并人工修正后，用一个 `applyAtomic` 事务提交「论文写入+删除 / 方法写入+删除 / 关系写入+删除」；
    并在日志里明确写出「已保留 N 处人工字段修正 / N 条人工修正关系」。
  - `genRelations()`：同样改用 `swap.write` + `repo.swapRelations`（模型结果不再覆盖人工修正，写删同事务）。

### 「原子替换」这句话的边界（如实说明）

- 现在**论文、方法、关系的写入与删除确实在同一个事务里完成**（`applyAtomic`），失败整体回滚。
- 但**分析产物不在这个事务里**：分歧 / 阅读路线 / 语料元信息 / 示例条件存在 `meta` store，按 `corpusId` 各自覆盖写入。
  它们失败时不会污染论文/方法/关系（那部分已提交或回滚），但严格说「整个案例加载是一个原子操作」并不成立 ——
  所以文档与注释统一表述为「**论文/方法/关系按一个事务替换；分析产物各自独立存档**」，不再笼统宣称整体原子。
