## 3. 没做的那一项：字段清单三份（需要核心 B 配合）

三处清单分别是：

- `cache.ts:24` `export const FIELD_KEYS_ORDER: FieldKey[] = [...]`（导出、被迁移与校验使用）
- `analyze.ts:74` `const FIELD_KEYS: FieldKey[] = [...]`（抽取循环用，**与上一份同序同内容**）
- `effective.ts:19` `export const FIELD_KEY_LIST = Object.keys(METHOD_FIELD_LABELS) as FieldKey[]`（人工修正读值用）

**为什么我没动**：收敛它至少要改 `cache.ts` 或 `effective.ts`，而这两个文件都在 01 文档的
`不要修改的范围` 里（越界要先在交付说明里列出原因、文件、接口变化与回滚方式，并**不静默修改**）。

**建议方案**（给能改这两个文件的人，或集成阶段统一做）：
把「字段清单」这个**公共词汇表**上收到 `src/core/types.ts`（已经是 `METHOD_FIELD_LABELS` 的家），
导出唯一一份 `FIELD_KEYS_ORDER`；`cache.ts` / `analyze.ts` / `effective.ts` 全部改为 import 它。
这样 `effective.ts` 还能顺手把 `Object.keys(METHOD_FIELD_LABELS)` 换成同一份显式列表 ——
目前它依赖「label map 的键序 == 字段顺序」这个隐含假设，一旦有人调整 label 顺序，人工修正的读值顺序就会跟着变。

**核心 A 侧可以先做的一小步**（如果你们同意，我随时做）：把 `analyze.ts` 的 `FIELD_KEYS` 改为
`import { FIELD_KEYS_ORDER } from '../cache'`（`cache.ts` 不 import `model/**`，不会成环）。
代价是抽取器依赖缓存模块的常量 —— 依赖方向不太漂亮，所以我没擅自做；
如果你们已决定由 `types.ts` 承载，那这一步就没必要，我直接等统一改造。
